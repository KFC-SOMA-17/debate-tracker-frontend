## 1. 기본 원칙

- 기능 구현 속도와 구조적 안정성을 함께 고려한다.
- 처음부터 과도한 아키텍처를 적용하지 않고, 도메인 기반 구조로 시작한다.
- 화면, 기능, 공통 UI의 책임을 명확히 분리한다.
- 서버 상태, 실시간 스트림 상태, UI 상태, 로컬 상태를 구분한다.
- 모든 상태를 전역 store에 모으지 않는다.
- API 요청/응답 타입과 UI에서 사용하는 타입은 필요에 따라 분리한다.
- 실시간 이벤트는 이벤트 종류별로 타입과 처리 흐름을 명확히 정의한다.
- 스타일과 포맷은 ESLint, Prettier에 위임한다.
- 코드 리뷰에서는 구조, 상태 책임, 타입 안정성, 예외 처리, 사용자 흐름을 우선 확인한다.

## 2. 폴더 구조

```
src
├─ app
├─ pages
├─ features
├─ shared
│  └─ ui
├─ api
├─ stores
├─ hooks
├─ types
├─ utils
└─ styles
```

### 각 영역의 역할

- `app`
  - 앱 진입점, 라우터, 전역 Provider, 앱 레벨 설정을 관리한다.
- `pages`
  - 라우팅 단위의 화면을 구성한다.
  - 여러 feature 컴포넌트를 조합한다.
  - 페이지 단위의 loading, error, empty, 접근 조건을 처리한다.
  - 복잡한 비즈니스 로직이나 실시간 이벤트 처리 로직은 직접 작성하지 않는다.
- `features`
  - 특정 기능과 관련된 컴포넌트, hook, 유틸, 타입을 관리한다.
  - 예: STT 속기록, 쟁점 요약, 마인드맵, 팀별 분석, 개인별 분석
- `shared/ui`
  - 도메인에 종속되지 않는 공통 UI 컴포넌트를 관리한다.
  - 예: Button, Card, Tabs, Chip, Modal, Accordion, SplitLayout
- `api`
  - HTTP API 요청 함수와 API client를 관리한다.
- `stores`
  - Zustand 기반 전역 UI 상태를 관리한다.
- `hooks`
  - 여러 기능에서 재사용되는 범용 hook을 관리한다.
- `types`
  - API 타입, socket 이벤트 타입, domain 타입, UI 타입을 관리한다.
- `utils`
  - 순수 유틸 함수를 관리한다.
- `styles`
  - 전역 스타일, 디자인 토큰, Tailwind 관련 설정을 관리한다.

## 3. 컴포넌트 작성 규칙

### 3-1. 공통 규칙

- 하나의 컴포넌트는 하나의 명확한 역할을 가진다.
- 데이터 조회, 이벤트 처리, UI 렌더링이 한 컴포넌트에 과도하게 섞이지 않도록 한다.
- JSX 구조가 길어지거나 조건 분기가 많아지면 하위 컴포넌트 또는 hook으로 분리한다.
- 단순히 줄 수를 줄이기 위한 분리는 지양한다.
- 의미 있는 UI 단위 또는 상태 단위로 분리한다.

### 3-2. 공통 컴포넌트

- 특정 도메인 데이터를 직접 알지 않는다.
- API 요청이나 Zustand store에 직접 접근하지 않는다.
- 텍스트, 상태, 이벤트 핸들러는 props로 전달받는다.
- `variant`, `size`, `disabled`, `loading`, `selected`, `active` 등으로 UI 상태를 표현한다.
- 도메인 로직이 들어가기 시작하면 feature 컴포넌트로 분리한다.

### 3-3. 기능 컴포넌트

- 공통 컴포넌트를 조합해 특정 기능을 구현한다.
- 서비스 도메인 타입, feature 내부 hook, feature 내부 유틸을 사용할 수 있다.
- 페이지 컴포넌트보다 작고, 공통 컴포넌트보다 도메인에 가깝게 유지한다.
- 컴포넌트가 커지면 UI 컴포넌트, custom hook, 유틸 함수, 타입 정의로 분리한다.

### 3-4. 페이지 컴포넌트

- 페이지 컴포넌트는 화면 조합에 집중한다.
- Header, Navigation, feature 컴포넌트를 배치한다.
- 페이지 단위의 loading, error, empty, 접근 조건을 처리한다.
- API 응답 변환, 실시간 이벤트 병합, 마인드맵 위치 계산 같은 복잡한 로직은 feature hook, store, utils, api layer로 분리한다.

## 4. 상태 관리 규칙

### 4-1. 상태 분류

- 서버 상태는 TanStack Query로 관리한다.
- 실시간 스트림 상태는 feature hook 또는 전용 store로 관리한다.
- 여러 화면에서 공유되는 UI 상태는 Zustand로 관리한다.
- 컴포넌트 내부에서만 필요한 상태는 `useState`로 관리한다.
- 서버 데이터를 Zustand에 중복 저장하지 않는다.
- 로컬 상태로 충분한 값을 전역 store에 올리지 않는다.

### 4-2. 서버 상태

- 서버에서 가져오고 캐싱이 필요한 데이터는 TanStack Query로 관리한다.
- query key는 도메인 단위로 명확하게 정의한다.
- mutation 이후 필요한 query만 invalidate한다.
- 서버 데이터를 화면에 맞게 가공해야 한다면 mapper 또는 query select를 사용한다.

### 4-3. 실시간 스트림 상태

- 실시간 STT 상태는 서버 상태와 분리한다.
- partial 발화와 final 발화를 구분한다.
- partial 발화는 현재 생성 중인 발화로 관리한다.
- final 이벤트가 도착하면 해당 발화를 확정 상태로 전환한다.
- 이벤트 식별자를 기준으로 중복 이벤트를 처리한다.
- 이벤트 순서 역전, 연결 끊김, 재연결 가능성을 고려한다.
- 페이지 이탈 또는 debateId 변경 시 기존 구독을 정리한다.

### 4-4. UI 전역 상태

- 여러 화면 또는 컴포넌트에서 공유해야 하는 UI 상태만 Zustand에 둔다.
- 예: split layout 크기, 패널 collapse 여부, 선택된 쟁점, 모달 열림 여부, 선택된 탭
- 화면 전환 후 유지되는 것이 자연스러운 상태만 storage persist를 고려한다.
- hover, 단순 accordion open 등 일시적 상태는 로컬 상태로 관리한다.

## 5. 타입 정의 규칙

### 5-1. API 타입

- API 요청 타입과 응답 타입은 분리한다.
- API 응답 타입은 서버 계약을 그대로 반영한다.
- 서버에서 내려주는 필드명, nullable 여부, enum 값을 임의로 바꾸지 않는다.
- 폼 입력값을 요청 타입으로 그대로 사용하지 않고, 필요한 경우 변환해서 전달한다.

### 5-2. UI 타입

- 서버 응답 타입이 UI에 적합하지 않으면 UI 타입을 따로 정의한다.
- 날짜 변환, snake_case / camelCase 변환, 중첩 구조 변환은 mapper에서 처리한다.
- 변환 로직을 컴포넌트 내부에 흩어놓지 않는다.

### 5-3. Socket 이벤트 타입

- Socket 이벤트는 이벤트 종류를 명확히 구분한다.
- 모든 이벤트는 이벤트 종류를 나타내는 필드를 가진다.
- partial, final, speaker update, correction 이벤트를 하나의 느슨한 타입으로 처리하지 않는다.
- 새로운 이벤트 타입이 추가되면 타입 정의, 이벤트 처리 로직, 관련 테스트를 함께 수정한다.
- 처리하지 않은 이벤트 타입이 조용히 무시되지 않도록 한다.

## 6. API 호출 규칙

- 초기 MVP에서는 native fetch 기반 custom API client를 사용한다.
- 인증 토큰 갱신, interceptor 기반 공통 처리, 복잡한 에러 처리가 필요해지면 Axios 도입을 재검토한다.
- 컴포넌트 내부에서 직접 fetch를 호출하지 않는다.
- 모든 HTTP 요청은 `api` 영역의 함수로 분리한다.
- 컴포넌트는 직접 URL과 HTTP method를 알지 않도록 한다.
- API client는 base URL, 공통 header, JSON parsing, HTTP error 변환, timeout 처리만 담당한다.
- 캐싱, refetch, retry, loading, error 상태는 TanStack Query가 담당한다.
- API 함수 이름은 `getData`, `postData`처럼 모호하게 짓지 않고 도메인 의미가 드러나게 작성한다.

---

## 7. Hook 작성 규칙

- hook은 컴포넌트에서 상태와 로직을 분리하기 위해 사용한다.
- feature에 종속된 hook은 해당 feature 내부에 둔다.
- 여러 도메인에서 재사용 가능한 hook만 공용 `hooks`에 둔다.
- hook 반환값은 객체 형태를 기본으로 한다.
- 동일한 로직이 반복되거나 컴포넌트 가독성이 떨어질 때 hook 분리를 검토한다.
- 단순한 한두 줄 상태 처리까지 무리하게 hook으로 분리하지 않는다.
- 실시간 구독, 자동 스크롤, split layout 계산, 마인드맵 interaction 등은 hook 분리 대상으로 고려한다.

---

## 8. 스타일링 규칙

- Tailwind CSS를 기본 스타일링 방식으로 사용한다.
- 디자인 토큰은 CSS Variables로 관리한다.
- 색상, 여백, radius, typography는 Tailwind와 디자인 토큰을 우선 사용한다.
- 동적으로 계산되는 좌표, 크기, transform, split layout 크기, 마인드맵 노드 위치는 inline style을 허용한다.
- 동일한 class 조합이 반복되면 공통 컴포넌트로 분리한다.
- 조건부 class가 복잡해지면 유틸 함수를 사용한다.
- className이 과도하게 길어지면 의미 있는 UI 단위로 분리한다.

## 9. 테스트 규칙

### 9-1. 파일 위치

- 테스트 파일은 테스트 대상 파일과 가까운 위치에 둔다.
- 테스트 파일명은 대상 파일명을 유지하고 `.test` 접미사를 사용한다.
- 한 feature 안에 테스트 파일이 많아지면 `__tests__` 폴더를 사용할 수 있다.
- 여러 테스트에서 공통으로 사용하는 mock 데이터는 fixture로 분리한다.

### 9-2. 작성 원칙

- 테스트는 구현 세부보다 외부에서 관찰 가능한 결과를 검증한다.
- 컴포넌트 내부 state 이름이나 내부 함수 호출 여부에 과도하게 의존하지 않는다.
- 컴포넌트 테스트는 사용자 행동과 화면 변화를 기준으로 작성한다.
- 순수 함수는 입력과 출력 중심으로 테스트한다.
- 비동기 동작은 결과 도착 전과 후의 상태를 구분해 검증한다.
- 스타일 자체, 외부 라이브러리 자체의 동작은 테스트하지 않는다.

### 9-3. 범위

- 모든 코드를 테스트 대상으로 삼지 않는다.
- 초기에는 핵심 로직과 주요 사용자 흐름을 우선 검증한다.
- 테스트 작성 비용이 기능 구현을 과도하게 방해하지 않도록 한다.
- 테스트하기 어려운 구조라면 테스트를 억지로 작성하기보다 코드 구조를 먼저 점검한다.

### 9-4. Mocking

- 외부 API나 네트워크 의존성이 있는 테스트는 MSW를 사용해 mock한다.
- mock은 실제 API 계약과 최대한 비슷하게 작성한다.
- 성공 응답뿐 아니라 필요한 경우 빈 응답, 지연 응답, 에러 응답도 검증한다.
