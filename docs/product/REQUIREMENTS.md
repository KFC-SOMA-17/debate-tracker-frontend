# 1. 서론

## 1.1 목적

- 본 문서는 디베이트 트래커 MVP 단계의 소프트웨어 요구사항을 정의한다.
- 개발팀은 본 문서를 기준으로 Sprint 1~6의 구현 범위와 완료 기준을 확인한다.
- 본 문서는 화면 설계서, API 명세서, 테스트 계획의 상위 기준으로 사용한다.
- 화면별 상세 UI 배치와 인터랙션은 별도 Figma 기반 화면 설계서에서 정의한다.
- REST API, WebSocket/STOMP 이벤트, 에러 응답 구조는 백엔드 구현 과정에서 별도 API 명세서로 작성한다.

## 1.2 문서 범위

- 본 문서는 다음 범위를 포함한다.
  - MVP 전체 기능 범위
  - 사용자와 사용 맥락
  - 페이지별 기능 요구사항
  - 상태 및 예외 요구사항
  - 외부 인터페이스 요구사항
  - 비기능 요구사항
  - Sprint별 구현 범위
  - 요구사항 검증 기준
- 본 문서는 다음을 상세히 다루지 않는다.
  - 구체적인 UI 픽셀 단위 디자인
  - API endpoint 최종 스펙
  - 데이터베이스 스키마
  - AI 모델별 프롬프트 상세
  - 배포 인프라 세부 설정

## 1.3 제품 개요

- 디베이트 트래커는 토론을 실시간으로 기록하고, 쟁점과 논증 구조를 정리하며, 토론 종료 후 분석 리포트와 산출물을 생성하는 웹 기반 서비스이다.
- 서비스의 핵심 흐름은 다음과 같다.
  - 랜딩 → 토론 준비 → 세션 워크스페이스 진입 후 실시간 음성 입력을 STT로 텍스트화한다.
  - 발화 내용을 정제하고 쟁점·주장·근거 구조로 정리한다.
  - 토론 종료 후 팀별 분석과 개인별 분석을 생성한다.
  - 분석 결과를 바탕으로 카드뉴스, 세특 참고 초안 등 목적별 산출물로 확장한다.

## 1.4 용어 정의

| 용어 | 정의 |
| --- | --- |
| 토론 세션 | 하나의 토론 진행 단위 |
| Public 레이어 | `debateId` 없이 접근하는 화면 영역 (`/` 랜딩, `/setup` 토론 준비) |
| Session 레이어 | 특정 `debateId`에 종속된 세션 워크스페이스 (`/debates/:debateId`) |
| STT | 음성을 텍스트로 변환하는 Speech-to-Text 기능 |
| 실시간 속기록 | 토론 중 발화를 실시간으로 텍스트화한 기록 |
| 쟁점 요약 | 발화를 기반으로 쟁점별 찬성/반대 주장과 근거를 구조화한 정보 |
| 주장 트리 | 주제, 주장, 근거를 노드와 엣지로 연결한 마인드맵형 시각화 |
| 팀별 분석 | 토론 종료 후 찬성/반대 팀 단위로 제공되는 사후 분석 |
| 개인별 분석 | 토론 종료 후 발화자별로 제공되는 사후 피드백 |
| 산출물 | 분석 결과를 바탕으로 생성되는 카드뉴스, 세특 참고 초안, PDF 리포트 등 |
| Partial 발화 | STT가 실시간으로 생성 중인 미확정 발화 |
| Final 발화 | STT가 확정 처리한 발화 |
| 사용자 | 토론자, 청중, 동아리 운영진, 교사, 판정 보조자 등 서비스 사용 주체 |

# 2. 전체 설명

## 2.1 제품 관점

- 본 서비스는 토론 활동을 단순히 녹음하거나 텍스트화하는 도구가 아니라, 토론 현장을 신뢰 가능한 텍스트 자산으로 전환하는 토론 전용 워크스페이스이다.
- 시스템은 크게 다음 세 영역으로 구성된다.
  - 실시간 토론 진행 영역
  - 사후 분석 영역
  - 산출물 생성 영역
- 사용자는 **랜딩(`/`) → 토론 준비(`/setup`) → 세션 워크스페이스(`/debates/:debateId`)** 순서로 새 토론에 진입한다.
- 실시간 토론 진행 영역은 Session 레이어 내 메인 대시보드에서 제공한다.
- 사후 분석 영역은 팀별 분석 페이지와 개인별 분석 페이지에서 제공한다.
- 산출물 생성 영역은 Sprint 5~6 이후 분석 결과를 기반으로 확장한다.

## 2.2 제품 기능 요약

| 기능군 | 주요 기능 | 구현 시점 |
| --- | --- | --- |
| F0. 진입·세션 생성 | 랜딩, 토론 준비, 세션 URL 진입 | Sprint 1 |
| F1. 실시간 토론 요약 | 실시간 속기록, 쟁점 요약, 주장 트리 | Sprint 1~2 |
| F2. 사후 토론 분석 | 팀별 분석, 개인별 분석, 개인 PDF 리포트 | Sprint 3~4 |
| F3. 산출물 자동화 | 카드뉴스 생성, 세특 참고 초안 생성 | Sprint 5~6 |

## 2.3 사용자 특성

| 사용자 | 주요 니즈 |
| --- | --- |
| 토론자 | 자신의 발언과 반박 흐름을 복기하고 개선점을 확인하고 싶다. |
| 청중/판정 보조자 | 토론 중 흐름과 쟁점을 놓치지 않고 따라가고 싶다. |
| 동아리 운영진 | 정기 토론 내용을 아카이빙하고 홍보 자료로 전환하고 싶다. |
| 교사 | 학생별 토론 활동 내용을 빠르게 정리하고 참고 자료로 활용하고 싶다. |
| 대회 운영자/판정관 | 판정 근거와 토론 흐름을 보조 자료로 확인하고 싶다. |

## 2.4 운영 환경

- MVP는 데스크톱 웹 환경을 기준으로 한다.
- 모바일 반응형 대응은 MVP 필수 범위에서 제외한다.
- 프론트엔드는 React, TypeScript, Vite 기반 SPA로 개발한다.
- 실시간 데이터는 WebSocket 또는 STOMP 기반으로 수신한다.
- 백엔드 API 명세가 확정되기 전까지 프론트엔드는 mock 데이터 기반으로 개발할 수 있다.

## 2.5 제약사항

- STT 정확도는 발화 환경, 마이크 품질, 주변 소음에 영향을 받을 수 있다.
- AI 요약 및 분석 결과는 사용자가 검토할 수 있는 참고 자료로 제공한다.
- 메인 대시보드에는 우세 판정, 점수, 승리 확률 등 사용자의 주관에 영향을 줄 수 있는 판단 정보를 표시하지 않는다.
- 개인별 분석에서는 공개 순위나 랭킹을 제공하지 않는다.
- 세특 초안은 공식 기록 자동 작성물이 아니라 교사용 참고 초안으로 제공한다.
- API 명세는 백엔드 구현 과정에서 별도 문서로 확정한다.

## 2.6 가정 및 의존성

- 사용자는 웹 브라우저에서 서비스를 사용한다.
- 사용자는 토론 준비 페이지(`/setup`)에서 토론 주제를 입력한다.
- 토론 진행 중 음성 입력이 가능해야 한다.
- 실시간 속기록과 쟁점 요약은 Session 레이어 진입 후 WebSocket/STOMP 이벤트 또는 서버 갱신 이벤트를 통해 업데이트된다.
- 사후 분석은 토론 종료 후 자동 또는 수동 트리거로 생성된다.
- 산출물 생성은 팀별/개인별 분석 결과가 존재하는 상태를 전제로 한다.

# 3. 외부 인터페이스 요구사항

## 3.1 사용자 인터페이스 요구사항

### UI-001. 공통 레이아웃

- 모든 주요 페이지는 Header를 포함해야 한다.
- 화면은 **Public 레이어**(`/` 랜딩, `/setup` 토론 준비)와 **Session 레이어**(`/debates/:debateId` 세션 워크스페이스)로 구분한다. URL·진입 조건·레이아웃 shell은 [`IA.md`](IA.md)를 따른다.
- Public 레이어
  - Header는 서비스명(및 로고)을 표시해야 한다.
  - `debateId`가 없는 상태에서는 토론 주제, 진행 상태, 녹음 상태를 노출하지 않아야 한다.
  - Global Navigation을 포함하지 않아야 한다.
  - 랜딩(`/`)은 `토론 시작` 버튼을 제공해야 한다.
  - 토론 준비(`/setup`)는 토론 주제 입력 폼과 `취소`, `토론 시작` 버튼을 제공해야 한다.
  - STT, 마이크, 실시간 데이터 수신을 활성화하지 않아야 한다.
- Session 레이어
  - Header와 Global Navigation을 포함해야 한다.
  - Header에는 서비스명, 토론 주제, 진행 상태, 진행 시간, 녹음 상태, 토론 종료 버튼을 표시해야 한다. (진행 중·종료 후 상태에 따라 항목 노출을 조절할 수 있다.)
  - Global Navigation은 메인 대시보드, 팀별 분석, 개인별 분석, 산출물 생성 메뉴를 포함해야 한다.
  - 현재 선택된 메뉴는 active 상태로 표시해야 한다.
  - 접근할 수 없는 메뉴는 disabled 상태로 표시해야 한다.

### UI-002. 메인 대시보드

- 메인 대시보드는 Session 레이어의 `/debates/:debateId`에서 제공되어야 한다.
- 메인 대시보드는 실시간 속기록 패널과 쟁점별 요약 패널을 함께 표시해야 한다.
- 두 패널은 resizable split layout으로 구성해야 한다.
- 사용자는 split bar를 드래그하여 패널 너비를 조절할 수 있어야 한다.
- threshold를 넘으면 한쪽 패널은 collapse되고, 다른 패널이 전체 영역을 차지해야 한다.
- 메인 대시보드 우측 하단에는 주장 트리 진입 버튼을 제공해야 한다.

### UI-003. 팀별 분석

- 팀별 분석은 하나의 리포트 페이지로 구성해야 한다.
- 팀별 종합 설득력 점수, 팀별 총평, 잘한 점, 아쉬운 점, 쟁점별 우세 판정을 표시해야 한다.
- 관련 발화를 확인할 수 있는 진입점을 제공해야 한다.

### UI-004. 개인별 분석

- 개인별 분석은 하나의 페이지에서 발화자 탭을 통해 리포트를 전환할 수 있어야 한다.
- 발화자 탭은 `찬성 1`, `찬성 2`, `반대 1` 형식으로 표시해야 한다.
- 선택된 발화자의 종합 평가와 발언별 피드백을 표시해야 한다.
- 선택된 발화자의 리포트를 PDF로 추출할 수 있는 진입점을 제공해야 한다.

### UI-005. 산출물 생성

- 산출물 생성 화면은 분석 결과 생성 이후 접근 가능해야 한다.
- 사용자는 산출물 유형을 선택할 수 있어야 한다.
- 산출물 유형은 카드뉴스와 세특 참고 초안을 우선 고려한다.
- 생성된 산출물은 사용자가 수정할 수 있어야 한다.

## 3.2 하드웨어 인터페이스 요구사항

- 사용자는 브라우저에서 마이크 입력 권한을 허용할 수 있어야 한다.
- 시스템은 사용자의 음성 입력을 STT 처리 대상으로 사용할 수 있어야 한다.
- 마이크 입력 실패 또는 권한 거부 시 사용자에게 상태를 안내해야 한다.
- 마이크 입력은 Session 레이어 진입 후 토론 진행 중에 활성화되어야 한다.

## 3.3 소프트웨어 인터페이스 요구사항

| 외부/내부 시스템 | 연동 목적 |
| --- | --- |
| STT API | 음성을 텍스트로 변환 |
| LLM API | 발화 보정, 쟁점 추출, 사후 분석, 산출물 생성 |
| REST API | 세션 생성, 분석 결과 조회, 산출물 생성 요청 |
| WebSocket/STOMP | 실시간 발화, 쟁점 요약, 주장 트리 업데이트 수신 |
| PDF 생성 모듈 | 개인별 분석 리포트 추출 |
| DB | 발화 원문, 정제 텍스트, 분석 결과, 산출물 저장 |

## 3.4 통신 인터페이스 요구사항

- 토론 진행 중 실시간 데이터는 WebSocket 또는 STOMP 기반으로 수신해야 한다.
- 실시간 연결은 Session 레이어(`/debates/:debateId`) 진입 후 시작되어야 한다.
- 토론 세션 생성, 종료, 분석 결과 조회, 산출물 생성 요청은 REST API 기반으로 처리한다.
- Socket 이벤트는 이벤트 타입과 payload 구조를 명확히 구분해야 한다.
- REST API와 Socket 이벤트 에러는 공통 error 객체 규격을 공유해야 한다.
- 실시간 연결 해제, 재연결, 중복 이벤트, 늦게 도착한 이벤트를 고려해야 한다.

# 4. 기능 요구사항

## 4.1 토론 세션 관리

### FR-001. 토론 시작

- 사용자는 랜딩(`/`)에서 `토론 시작` 버튼을 클릭할 수 있어야 한다.
- `토론 시작` 클릭 시 시스템은 토론 준비 페이지(`/setup`)로 이동해야 한다.
- 사용자는 토론 준비 페이지에서 토론 주제를 입력할 수 있어야 한다.
- 토론 주제가 비어 있으면 `토론 시작` 요청을 보낼 수 없어야 한다.
- 사용자가 `취소`를 클릭하면 랜딩(`/`)으로 돌아가야 한다.
- 사용자가 `토론 시작`을 클릭하면 시스템은 토론 세션 생성 요청을 전송해야 한다.
- 세션 생성 요청 중에는 중복 요청을 허용하지 않아야 한다.
- 세션 생성 성공 시 시스템은 `/debates/:debateId`로 이동하고 토론 진행 중 상태로 전환해야 한다.
- 세션 생성 성공 후 Session 레이어에서 실시간 속기록 수신 및 마이크 입력 준비 상태로 전환해야 한다.
- 세션 생성 실패 시 토론 준비 페이지 내부에 오류 상태를 표시해야 한다.
- 진행 중인 토론 세션이 클라이언트에 추적되는 경우, 사용자가 `/` 또는 `/setup`에 진입하면 현재 `/debates/:debateId`로 redirect할 수 있다. (세션 상태 복원은 MVP에서 보장하지 않는다.)

### FR-002. 토론 종료

- 사용자는 Session 레이어에서 토론 진행 중 토론 종료 버튼을 클릭할 수 있어야 한다.
- 시스템은 토론 종료 확인 모달을 표시해야 한다.
- 사용자가 취소를 클릭하면 토론 진행 상태를 유지해야 한다.
- 사용자가 종료를 확인하면 시스템은 토론 종료 요청을 전송해야 한다.
- 종료 성공 시 시스템은 토론 상태를 종료 또는 분석 생성 중으로 변경해야 한다.
- 토론 종료 후 팀별 분석과 개인별 분석은 분석 생성 상태를 표시해야 한다.
- 토론 종료 실패 시 오류 상태를 표시해야 한다.

## 4.2 실시간 속기록

### FR-101. 발화 표시

- 시스템은 STT를 통해 변환된 발화를 실시간으로 표시해야 한다.
- 발화는 카드 리스트 형태로 표시해야 한다.
- 각 발화 카드는 발화 시작 시각, 화자 번호, 발화 내용을 포함해야 한다.
- 화자 번호는 `찬성 1`, `찬성 2`, `반대 1` 형식으로 표시해야 한다.
- 발화 내용이 길어도 카드 내부에서 텍스트가 겹치지 않아야 한다.
- 발화 목록이 많아지면 스크롤 가능한 리스트로 제공해야 한다.

### FR-102. Partial/Final 발화 처리

- 시스템은 생성 중인 partial 발화와 확정된 final 발화를 구분해야 한다.
- partial 발화는 typing 중인 상태처럼 표시해야 한다.
- 같은 발화의 partial 이벤트가 여러 번 수신되면 기존 partial을 갱신해야 한다.
- final 이벤트가 수신되면 해당 발화를 확정 발화 목록으로 전환해야 한다.
- partial과 final 발화가 중복 표시되지 않아야 한다.
- 중복 이벤트 또는 늦게 도착한 이벤트에 의해 발화 순서가 깨지지 않도록 처리해야 한다.

### FR-103. 실시간 연결 상태

- 시스템은 STT 연결 전, 연결 중, 연결 실패, 재연결 중, 수신 중 상태를 표시할 수 있어야 한다.
- 연결 실패 시 사용자가 현재 상황을 이해할 수 있는 메시지를 표시해야 한다.
- 재연결이 가능한 경우 재시도 또는 자동 재연결 상태를 표시해야 한다.

## 4.3 쟁점별 요약

### FR-201. 쟁점 탭 제공

- 시스템은 토론 중 추출된 쟁점을 탭 형태로 제공해야 한다.
- 사용자는 쟁점 탭을 클릭해 선택된 쟁점의 내용을 확인할 수 있어야 한다.
- 선택된 쟁점 탭은 active 상태로 표시해야 한다.
- 쟁점이 아직 생성되지 않은 경우 빈 상태를 표시해야 한다.

### FR-202. 쟁점별 찬반 주장 표시

- 시스템은 선택된 쟁점에 대해 찬성 측 주장과 반대 측 주장을 좌우 비교 형태로 표시해야 한다.
- 각 주장에는 세부 근거를 포함해야 한다.
- 세부 근거는 accordion 형태로 제공해야 한다.
- Sprint 1에서는 세부 근거 accordion을 기본 펼침 상태로 제공한다.
- 세부 근거에는 가능한 경우 통계, 사례, 인용 등 근거 유형을 표시해야 한다.
- 메인 대시보드에서는 우세 판정, 승리 확률, 점수 등 주관적 판단 정보를 표시하지 않아야 한다.

### FR-203. 쟁점 요약 갱신

- 쟁점 요약은 실시간 발화 누적에 따라 갱신될 수 있어야 한다.
- 쟁점 갱신 중 기존 UI가 과도하게 흔들리지 않아야 한다.
- 선택된 쟁점은 가능한 경우 갱신 후에도 유지해야 한다.
- 요약 생성 중, 요약 없음, 요약 실패 상태를 표시해야 한다.

## 4.4 Resizable Split Layout

### FR-301. 패널 크기 조절

- 사용자는 메인 대시보드의 split bar를 드래그해 실시간 속기록 패널과 쟁점 요약 패널의 너비를 조절할 수 있어야 한다.
- 크기 조절 중 레이아웃이 끊기거나 패널 내용이 겹치지 않아야 한다.
- 기본 분할 비율은 Figma 화면 설계를 따른다.

### FR-302. 패널 Collapse

- 특정 threshold를 넘으면 한쪽 패널이 collapse되어야 한다.
- STT 패널이 collapse되면 쟁점 요약 패널이 전체 영역을 차지해야 한다.
- 쟁점 요약 패널이 collapse되면 STT 패널이 전체 영역을 차지해야 한다.
- collapse 상태에서 사용자는 다시 기본 분할 상태로 복귀할 수 있어야 한다.

## 4.5 마인드맵 주장 트리

### FR-401. 주장 트리 모달

- 시스템은 메인 대시보드 우측 하단에 실시간 주장 트리 Floating Button을 제공해야 한다.
- 사용자가 버튼을 클릭하면 전체 모달 형태의 주장 트리 화면을 표시해야 한다.
- 모달은 사용자가 명시적으로 닫을 수 있어야 한다.

### FR-402. 주장 트리 시각화

- 주장 트리는 주제, 주장, 근거를 노드와 엣지로 연결해 표시해야 한다.
- 노드는 주제, 주장, 근거 유형을 가질 수 있어야 한다.
- 사용자는 노드를 Drag & Drop으로 이동할 수 있어야 한다.
- 사용자는 마인드맵 영역을 zoom-in/zoom-out 할 수 있어야 한다.
- 사용자는 배경을 드래그하여 pan 할 수 있어야 한다.
- 마인드맵은 스크롤 기반이 아니라 zoom/pan 기반 탐색 경험을 제공해야 한다.

### FR-403. 주장 트리 상호작용

- 사용자가 특정 노드에 hover하면 관련 노드와 엣지만 강조해야 한다.
- 관련 없는 노드와 엣지는 흐리게 표시해야 한다.
- 사용자가 특정 노드를 클릭하면 오른쪽 상세 패널을 표시해야 한다.
- 상세 패널은 최초 진입 시 닫혀 있어야 한다.
- 상세 패널에는 선택된 노드와 관련된 주장, 근거, 관련 발화를 표시할 수 있어야 한다.

## 4.6 팀별 분석

### FR-501. 팀별 분석 접근

- 팀별 분석 페이지는 토론 종료 후 접근 가능해야 한다.
- 토론 진행 중에는 팀별 분석 메뉴를 disabled 상태로 표시해야 한다.
- 분석 생성 중에는 loading 상태를 표시해야 한다.
- 분석 실패 시 error 상태와 재시도 가능성을 표시해야 한다.

### FR-502. 팀별 종합 분석

- 시스템은 찬성 측과 반대 측의 종합 설득력 점수를 표시해야 한다.
- 점수는 참고 지표로 제공하며, 점수만으로 결과를 단정하지 않아야 한다.
- 각 팀에 대한 한 줄 총평 또는 종합 피드백을 함께 표시해야 한다.
- 각 팀에 대해 잘한 점, 아쉬운 점, 개선 방향을 제공해야 한다.

### FR-503. 쟁점별 우세 판정

- 시스템은 주요 쟁점별로 상대적으로 우세한 팀을 표시할 수 있어야 한다.
- 우세 판정은 단순 발화 수나 근거 수 비교가 아니라 질적 설명 중심으로 제공해야 한다.
- 각 쟁점별 판정 이유를 서술형으로 제공해야 한다.
- 판정 근거가 되는 관련 발화를 확인할 수 있는 진입점을 제공해야 한다.

## 4.7 개인별 분석

### FR-601. 개인별 분석 접근

- 개인별 분석 페이지는 토론 종료 후 접근 가능해야 한다.
- 토론 진행 중에는 개인별 분석 메뉴를 disabled 상태로 표시해야 한다.
- 분석 생성 중에는 loading 상태를 표시해야 한다.
- 분석 실패 시 error 상태와 재시도 가능성을 표시해야 한다.

### FR-602. 발화자별 리포트 전환

- 시스템은 발화자별 분석 결과를 탭으로 전환할 수 있게 제공해야 한다.
- 발화자 탭은 `찬성 1`, `찬성 2`, `반대 1` 형식으로 표시해야 한다.
- 선택된 발화자는 active 상태로 표시해야 한다.
- 발화자 탭은 순위나 랭킹처럼 보이지 않게 구성해야 한다.

### FR-603. 개인 종합 평가

- 시스템은 선택된 발화자의 종합 피드백을 서술형으로 제공해야 한다.
- 개인 종합 점수나 공개 랭킹은 MVP에서 제공하지 않는다.
- 평가에는 강점, 보완점, 추천 연습 방향을 포함해야 한다.
- 개인이 수용하기 어려운 단정적 표현은 지양해야 한다.

### FR-604. 개인 발언별 피드백

- 시스템은 선택된 발화자의 주요 발언별 피드백을 카드 형태로 제공해야 한다.
- 각 피드백 카드는 발화 원문, 관련 쟁점, 좋았던 점, 보완할 점, 개선 제안을 포함해야 한다.
- 점수보다 서술형 피드백을 우선 표시해야 한다.

### FR-605. 개인 PDF 리포트 추출

- 시스템은 선택된 발화자의 개인 리포트를 PDF로 추출할 수 있어야 한다.
- PDF에는 토론 주제, 발화자 번호, 개인 종합 평가, 주요 발언별 피드백을 포함해야 한다.
- PDF 생성 중, 생성 실패, 생성 완료 상태를 표시해야 한다.
- MVP에서는 PDF 디자인 완성도보다 추출 흐름을 우선한다.

## 4.8 산출물 생성

### FR-701. 산출물 생성 접근

- 산출물 생성 페이지는 분석 결과 생성 이후 접근 가능해야 한다.
- 분석 결과가 없는 경우 산출물 생성 메뉴는 disabled 상태로 표시해야 한다.
- 사용자는 산출물 유형을 선택할 수 있어야 한다.

### FR-702. 세특 참고 초안 생성

- 시스템은 개인별 분석 결과를 기반으로 세특 작성 참고 초안을 생성할 수 있어야 한다.
- 초안은 공식 기록 자동 작성물이 아니라 교사가 검토하고 수정할 참고 자료로 제공해야 한다.
- 생성된 초안은 사용자가 직접 수정할 수 있어야 한다.
- 글자 수 제한을 설정하거나 표시할 수 있어야 한다.
- 생성 결과는 복사하거나 저장할 수 있어야 한다.

### FR-703. 카드뉴스 생성/에디터

- 시스템은 토론 내용을 기반으로 카드뉴스 초안을 생성할 수 있어야 한다.
- 카드뉴스에는 토론 주제, 핵심 쟁점, 찬성 측 주장, 반대 측 주장, 주요 근거, 토론 요약을 포함할 수 있어야 한다.
- 사용자는 생성된 카드뉴스 내용을 수정할 수 있어야 한다.
- Sprint 범위에 따라 텍스트 수정과 카드별 내용 편집을 우선 제공한다.
- 이미지 편집, 템플릿 마켓, SNS 연동은 후순위로 둔다.

# 5. 비기능 요구사항 (기획서에 있는 내용만 포함)

## 5.1 성능 요구사항

### NFR-001. 실시간 STT 표시 지연

- 시스템은 STT 변환 결과를 사용자가 실시간으로 따라갈 수 있는 수준으로 표시해야 한다.
- 기획 단계 목표로 STT 발화 텍스트는 발화 후 2~5초 이내 화면 반영을 목표로 한다.

### NFR-002. 쟁점 요약 갱신 주기

- 쟁점 요약은 토론 흐름을 따라갈 수 있도록 주기적으로 갱신되어야 한다.
- 기획 단계 목표로 쟁점 요약과 LLM 기반 보정은 10~20초 주기 업데이트를 목표로 한다.

### NFR-003. UI 반응성

- split bar drag, 마인드맵 zoom/pan/drag 등 주요 인터랙션은 사용자가 지연을 체감하지 않도록 동작해야 한다.
- 긴 발화나 쟁점 갱신으로 인해 UI 레이아웃이 깨지지 않아야 한다.

## 5.2 신뢰성 및 복구성 요구사항

### NFR-101. 연결 복구

- 실시간 연결이 일시적으로 끊길 수 있음을 고려해야 한다.
- 시스템은 재연결 중 상태를 사용자에게 표시할 수 있어야 한다.
- 가능한 경우 재연결 이후 누락된 발화를 복구하거나 재동기화할 수 있어야 한다.

### NFR-102. 이벤트 정합성

- 시스템은 중복 이벤트, 늦게 도착한 이벤트, partial/final 이벤트 순서 문제를 고려해야 한다.
- 발화 목록은 가능한 경우 발화 시작 시각 또는 서버 sequence 기준으로 정렬되어야 한다.

### NFR-103. 분석 실패 대응

- 분석 생성 실패 시 사용자가 실패 상태를 인지할 수 있어야 한다.
- 재시도가 가능한 경우 재시도 진입점을 제공해야 한다.

## 5.3 사용성 요구사항

### NFR-201. 실시간 화면 인지 부담 완화

- 메인 대시보드에서는 실시간 속기록과 쟁점 요약을 함께 제공하되, 사용자가 패널 크기를 조절할 수 있어야 한다.
- 메인 대시보드에는 승패 판단이나 점수처럼 토론 중 주관에 영향을 줄 수 있는 정보는 표시하지 않는다.

### NFR-202. 개인 분석 심리적 부담 완화

- 개인별 분석은 공개 순위나 랭킹을 제공하지 않는다.
- 피드백은 점수보다 서술형 개선 방향 중심으로 제공한다.

### NFR-203. 용어 이해성

- 전문 용어가 필요한 경우 설명을 함께 제공할 수 있어야 한다.
- STT, 쟁점, 근거 유형, 설득력 점수 등 사용자가 이해해야 하는 정보는 명확한 라벨로 표시해야 한다.

## 5.4 보안 및 개인정보 요구사항

### NFR-301. 음성 및 발화 데이터 보호

- 토론 음성, 발화 텍스트, 분석 결과는 민감한 활동 데이터로 취급해야 한다.
- 사용자의 동의 없이 개인별 분석 결과를 공개적으로 노출하지 않아야 한다.
- 개인별 분석 접근 정책은 후속 기획에서 명확히 정의한다.

### NFR-302. 데이터 접근 제어

- 토론 세션 데이터는 해당 세션 접근 권한을 가진 사용자만 조회할 수 있어야 한다.
- MVP에서는 권한 시스템을 단순화하되, 추후 권한 관리 확장을 고려한 구조로 설계한다.

## 5.5 유지보수성 요구사항

### NFR-401. 기능 확장성

- 실시간 속기록, 쟁점 요약, 주장 트리, 팀별 분석, 개인별 분석, 산출물 생성은 기능 단위로 분리되어야 한다.
- 추후 산출물 유형, 분석 항목, AI 모델 변경에 대응할 수 있도록 데이터 구조와 UI 구조를 분리한다.

### NFR-402. 오류 처리 일관성

- REST API와 Socket 이벤트의 에러는 공통 error 객체 규격을 공유해야 한다.
- 프론트엔드는 error code와 recoverable 여부를 기준으로 페이지 단위, 패널 단위, 액션 단위 오류를 분기할 수 있어야 한다.

## 5.6 이식성 및 호환성 요구사항

### NFR-501. 브라우저 호환성

- MVP는 최신 Chrome 기반 데스크톱 브라우저를 우선 지원한다.
- Safari, Firefox 대응은 주요 기능 안정화 이후 검토한다.

### NFR-502. 반응형 범위

- MVP는 데스크톱 웹 환경을 기준으로 한다.
- 모바일 최적화는 MVP 범위에서 제외한다.

# 7. 상태 및 예외 요구사항

## 7.1 공통 상태

| 상태 | 설명 |
| --- | --- |
| loading | 데이터 또는 분석 결과를 불러오는 중 |
| empty | 표시할 데이터가 없는 상태 |
| error | 데이터 조회 또는 분석 생성에 실패한 상태 |
| disabled | 접근할 수 없는 기능 또는 페이지 |
| active | 현재 선택된 메뉴, 탭, 항목 |
| selected | 사용자가 선택한 노드, 발화자, 항목 |
| streaming | 실시간 데이터가 생성 중인 상태 |
| completed | 생성 또는 분석이 완료된 상태 |

## 7.2 실시간 데이터 예외

- STT 연결이 지연될 수 있다.
- STT 연결이 실패할 수 있다.
- 발화자 식별이 늦게 도착할 수 있다.
- partial 발화가 여러 번 갱신될 수 있다.
- final 발화가 늦게 도착할 수 있다.
- 같은 이벤트가 중복으로 도착할 수 있다.
- 네트워크 재연결이 발생할 수 있다.
- 쟁점 요약 갱신 중 기존 화면이 흔들릴 수 있다.
- 긴 발화가 UI 레이아웃을 깨뜨릴 수 있다.

## 7.3 분석 결과 예외

- 토론 종료 직후 분석 결과가 아직 생성되지 않았을 수 있다.
- 분석 생성에 실패할 수 있다.
- 분석 결과 중 일부만 생성될 수 있다.
- 특정 발화자에 대한 개인 분석이 없을 수 있다.
- 특정 쟁점에 대한 근거 발화가 부족할 수 있다.
- 분석 결과의 신뢰도가 낮을 수 있다.

## 7.4 산출물 생성 예외

- 산출물 생성에 실패할 수 있다.
- 생성 결과가 사용자의 기대와 다를 수 있다.
- 글자 수 제한을 초과할 수 있다.
- 카드뉴스 내용이 너무 길어질 수 있다.
- 사용자가 직접 수정할 필요가 있을 수 있다.
- 세특 참고 초안은 공식 기록이 아니라 참고 자료임을 명확히 해야 한다.

## 7.5 진입·세션 예외

- 진행 중 세션이 클라이언트에 추적되는 동안 `/` 또는 `/setup` 재진입 시 현재 세션 URL로 redirect될 수 있다.
- 새로고침 또는 앱 재시작 후에는 클라이언트 세션 추적이 초기화되어 redirect가 동작하지 않을 수 있다.
- 세션 URL(`/debates/:debateId`) 직접 진입 시 서버 조회 API가 없으면 토론 주제·속기록·phase를 복원하지 못할 수 있다.
- 토론 주제는 세션 생성 직후 navigate state로 전달되며, 새로고침 시 소실될 수 있다.

## 8.3 Sprint별 완료 기준

### Sprint 1 완료 기준

- 랜딩(`/`)과 토론 준비(`/setup`) 페이지가 표시된다.
- 사용자는 랜딩에서 `토론 시작`을 클릭해 토론 준비 페이지로 이동할 수 있다.
- 사용자는 토론 준비 페이지에서 토론 주제를 입력해 토론 세션을 시작할 수 있다.
- 세션 생성 성공 시 `/debates/:debateId`로 이동하고 토론 진행 중 상태가 표시된다.
- Public 레이어에서는 STT·마이크·Global Navigation이 활성화되지 않는다.
- Session 레이어에서 실시간 속기록 패널이 표시된다.
- 발화 카드가 발화 시작 시각, 화자 번호, 발화 내용을 표시한다.
- partial 발화와 final 발화가 구분된다.
- 쟁점별 요약 패널이 표시된다.
- 쟁점 탭을 전환할 수 있다.
- 찬성/반대 주장이 좌우로 구분되어 표시된다.
- 세부 근거가 accordion 형태로 표시된다.
- split bar를 통해 두 패널 크기를 조절할 수 있다.
- 한쪽 패널 collapse 시 남은 패널이 전체 영역을 차지한다.
- mock 데이터 기준으로 화면이 정상 동작한다.

### Sprint 2 완료 기준

- 실시간 주장 트리 모달을 열고 닫을 수 있다.
- 주제, 주장, 근거 노드가 연결된 구조로 표시된다.
- 노드를 자유롭게 Drag & Drop 할 수 있다.
- zoom-in/zoom-out이 가능하다.
- 배경 pan이 가능하다.
- 노드 hover 시 관련 노드와 엣지만 강조된다.
- 노드 클릭 시 오른쪽 상세 패널이 열린다.
- 실시간 속기록과 쟁점 요약의 주요 UI 문제를 개선한다.
- Sprint 1 기능이 회귀 없이 동작한다.

### Sprint 3 완료 기준

- 토론 종료 후 팀별 분석 페이지에 접근할 수 있다.
- 팀별 종합 설득력 점수가 표시된다.
- 팀별 총평이 표시된다.
- 잘한 점과 아쉬운 점이 표시된다.
- 쟁점별 우세 판정이 표시된다.
- 관련 발화를 확인할 수 있는 진입점이 제공된다.
- loading, empty, error 상태가 표시된다.

### Sprint 4 완료 기준

- 토론 종료 후 개인별 분석 페이지에 접근할 수 있다.
- 발화자 탭을 전환할 수 있다.
- 선택된 발화자의 종합 평가가 표시된다.
- 선택된 발화자의 발언별 피드백이 표시된다.
- PDF 리포트 발행 버튼이 표시된다.
- 선택된 발화자의 리포트를 PDF로 추출할 수 있다.
- loading, empty, error 상태가 표시된다.

### Sprint 5~6 완료 기준

- 분석 결과를 기반으로 산출물 생성 페이지에 접근할 수 있다.
- 산출물 유형을 선택할 수 있다.
- 세특 참고 초안 또는 카드뉴스 초안을 생성할 수 있다.
- 생성된 산출물을 수정할 수 있다.
- 산출물을 복사, 저장, 보내기할 수 있는 진입점이 제공된다.
- loading, empty, error 상태가 표시된다.

# 10. 후순위 및 제외 범위
